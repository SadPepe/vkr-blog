# Домашний хостинг: белый IP + Caddy

Вариант для случая, когда VPS дорого, а ПК находится в России: база, файлы и бэкапы
остаются в РФ, требования 152-ФЗ по локализации выполняются. Наружу смотрит только
Caddy на `80/443`; приложение и PostgreSQL доступны лишь внутри compose-сети.

Схема:

```
интернет → роутер (проброс 80/443) → Caddy → app (nginx + php-fpm) → db
```

Cloudflare в режиме **Proxied** и Cloudflare Tunnel для этого варианта не подходят:
трафик и IP посетителей проходят через зарубежную компанию, а это трансграничная
передача персональных данных. Cloudflare допустим только как DNS в режиме
**DNS only**, но надёжнее использовать DNS российского регистратора.

## Когда вариант подходит

- у провайдера есть **статический публичный IPv4** (или динамический + DDNS);
- входящие `80/tcp` и `443/tcp` не заблокированы;
- ПК может работать круглосуточно, желательно с UPS;
- адрес и данные находятся в РФ.

Не подходит, если провайдер использует CGNAT или режет входящие порты: проброс
портов в этом случае не заработает. Тогда нужен белый IP у провайдера либо
российский VPS.

## 1. Проверить IP и отсутствие CGNAT

Сравните WAN-IP в роутере с адресом, который видит интернет:

```powershell
(Invoke-RestMethod https://api.ipify.org)
```

Если адреса разные или WAN попадает в `100.64.0.0/10` — это CGNAT. Уточните у
провайдера: «статический публичный IPv4, без CGNAT, входящие 80 и 443 разрешены».
Проверить доступность портов снаружи можно с мобильного интернета или внешним
сервисом проверки портов.

### Пример: МТС / МГТС

МТС предлагает услугу статического IP для домашнего интернета GPON/FTTB/ADSL:
подключение бесплатно, абонентская плата около 179 ₽/мес, доступность зависит от
региона. Провайдер заявляет отсутствие блокировки входящих TCP/UDP-портов — для
Caddy этого достаточно.

Перед оплатой всё равно попросите поддержку подтвердить: **публичный IPv4 без
CGNAT**, входящие `80` и `443` не фильтруются, адрес выдаётся на ваш роутер. После
подключения проверьте, что WAN-IP роутера совпадает с `api.ipify.org`, и что порты
доступны снаружи. Если перед роутером стоит ONT провайдера, нужен bridge-режим или
DMZ на роутер, иначе получится двойной NAT и проброс портов не сработает.

## 2. Домен и DNS

- A-запись домена → ваш публичный IP. AAAA добавляйте только если IPv6 действительно
  работает и firewall открыт, иначе часть клиентов не сможет подключиться.
- Динамический IP → DDNS: скрипт/клиент провайдера или API регистратора обновляет
  A-запись. CGNAT DDNS не обходит.
- Cloudflare: только «DNS only» (серое облако). Не включайте прокси и не используйте
  Tunnel — см. вступление.
- Проверка: `Resolve-DnsName ваш-домен.ру`.

## 3. Роутер и Windows Firewall

1. Зарезервируйте локальный IP ПК по MAC в DHCP роутера.
2. Пробросьте на этот IP: `80/tcp`, `443/tcp`; при желании HTTP/3 — `443/udp`.
3. **Не пробрасывайте** `8080` и `5432`: приложение и БД не должны быть видны снаружи.
4. Разрешите входящие 80/443 в Windows Firewall (PowerShell от администратора):

```powershell
New-NetFirewallRule -DisplayName "vkr-blog HTTP" -Direction Inbound -Protocol TCP -LocalPort 80 -Action Allow
New-NetFirewallRule -DisplayName "vkr-blog HTTPS" -Direction Inbound -Protocol TCP -LocalPort 443 -Action Allow
```

Проверьте, что порты не заняты IIS или другим веб-сервером:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 80,443 |
    Select-Object LocalAddress, LocalPort, OwningProcess
```

Если порт 80 занят службой `W3SVC` (IIS), остановите и отключите её.

## 4. Windows и Docker

- Docker Desktop с бэкендом WSL2, включите автозапуск: Settings → General →
  «Start Docker Desktop when you sign in».
- Автовход в Windows (Docker Desktop запускается в сессии пользователя) или
  Docker Engine внутри WSL с systemd и задачей планировщика.
- Электропитание: сон и гибернация — «Никогда», обновления Windows — активные часы,
  чтобы ПК не перезагружался в случайный момент.
- `restart: unless-stopped` уже задан в `docker-compose.yml`.
- После перезагрузки проверьте: `docker compose ps`, затем `/up`.

## 5. Настройки `.env` для продакшена

Скопируйте шаблон и заполните значения:

```powershell
Copy-Item .env.production.example .env
```

Обязательно:

| Переменная | Значение |
|---|---|
| `APP_ENV` | `production` |
| `APP_DEBUG` | `false` |
| `APP_URL` | `https://ваш-домен.ру` |
| `APP_DOMAIN` | `ваш-домен.ру` |
| `ACME_EMAIL` | ваша почта для Let's Encrypt |
| `SESSION_SECURE_COOKIE` | `true` |
| `APP_BIND` | `127.0.0.1` (наружу отдаёт Caddy) |
| `DB_PASSWORD` | длинный случайный пароль |
| `PRIVATE_BETA` | `true` до публичного запуска, затем `false` |
| `REGISTRATION_INVITE_CODE` | пусто для открытой регистрации |
| `LEGAL_*` | реальные реквизиты оператора |

`APP_KEY` должен быть постоянным, иначе сессии и зашифрованные cookie сбрасываются
при каждом перезапуске. Сгенерируйте ключ и вставьте его в `.env`:

```powershell
docker compose up -d --build app db
docker compose exec app php artisan key:generate --show
```

Затем примените настройки — именно `up`, а не `restart`: переменные окружения
фиксируются при создании контейнера.

```powershell
docker compose up -d app
```

Почта для восстановления пароля — российский SMTP (`MAIL_*` в шаблоне). Зарубежный
почтовый сервис нарушает утверждение об отсутствии трансграничной передачи.

### Почта: два варианта

**Вариант A — бесплатно, личный ящик.** Заведите обычный ящик на Яндексе или Mail.ru
(оба в РФ) и используйте его SMTP:

| Провайдер | SMTP | Порт | Схема | Пароль |
|---|---|---|---|---|
| Яндекс | `smtp.yandex.ru` | `465` | `smtps` | пароль приложения |
| Mail.ru | `smtp.mail.ru` | `465` | `smtps` | пароль приложения |

Пароль приложения создаётся в настройках безопасности аккаунта (для Яндекса —
«Пароли приложений»), обычный пароль от почты для SMTP не подойдёт. В `.env`:

```dotenv
MAIL_MAILER=smtp
MAIL_SCHEME=smtps
MAIL_HOST=smtp.yandex.ru
MAIL_PORT=465
MAIL_USERNAME=ваш-ящик@yandex.ru
MAIL_PASSWORD=пароль-приложения
MAIL_FROM_ADDRESS="ваш-ящик@yandex.ru"
```

`MAIL_FROM_ADDRESS` должен совпадать с ящиком: писать `no-reply@chelnipodzemka.ru`
без почты на домене нельзя — не пройдут SPF/DKIM, письма уйдут в спам. Этот же
адрес можно указать в `LEGAL_EMAIL`. Для диплома вариант достаточный.

**Вариант B — почта на домене.** Нужен платный сервис: Яндекс 360 для бизнеса
(около 319 ₽/мес) или VK WorkSpace (около 309 ₽/мес), тарифы меняются. Порядок:

1. Добавьте домен в кабинет провайдера и подтвердите владение TXT-записью.
2. Пропишите у регистратора MX, SPF, DKIM и DMARC — провайдер даёт точные значения.
3. Создайте ящики `privacy@chelnipodzemka.ru` и `no-reply@chelnipodzemka.ru`.
4. Возьмите SMTP-параметры из справки провайдера (обычно порт `465`, схема `smtps`).
5. Укажите их в `MAIL_*`, а `MAIL_FROM_ADDRESS=no-reply@chelnipodzemka.ru`.

Корпоративные тарифы обычно рассчитаны на ИП/самозанятых или организацию — уточните
условия. Не направляйте MX на зарубежный сервис и не используйте Cloudflare Email
Routing: это противоречит локализации.

После правки `.env` пересоздайте контейнер и проверьте отправку:

```powershell
docker compose up -d app
docker compose exec app php artisan tinker
```

В консоли tinker:

```php
Mail::raw('test', fn ($m) => $m->to('ваш-ящик@example.ru')->subject('test'));
```

Письмо должно прийти в течение минуты; если нет — смотрите `docker compose logs app`
и папку «Спам». После смены `MAIL_*` не забудьте `docker compose up -d app`.

Если том `db` уже создан, смена `DB_USERNAME`/`DB_PASSWORD` в `.env` не меняет
пользователя и пароль в PostgreSQL: `POSTGRES_*` применяются только при первой
инициализации. Для существующей базы проще оставить прежние значения. Если пароль
нужно сменить, сделайте это внутри БД, а потом обновите `.env` и пересоздайте `app`:

```powershell
docker compose exec db psql -U postgres -d blog -c "ALTER USER blog WITH PASSWORD 'новый-пароль';"
```

Смена `DB_USERNAME` на другого пользователя требует создания роли и выдачи прав на
существующие таблицы; без необходимости не меняйте её. Чистая установка (пустой том
`db`) использует значения из `.env` без дополнительных действий.

## 6. Запуск с HTTPS

DNS уже указывает на ваш IP, порты открыты:

```powershell
docker compose --profile https up -d --build
docker compose logs -f caddy
```

Проверка:

```powershell
curl.exe -I https://ваш-домен.ру/up      # 200
curl.exe -I http://ваш-домен.ру          # 301/308 на https
curl.exe -I http://127.0.0.1:8080/       # 200, только локально
```

Caddy сам выпускает и продлевает сертификат Let's Encrypt. Тома `caddy_data` и
`caddy_config` не удаляйте: там сертификаты. `docker compose down -v` стирает их
и базу — не используйте эту команду на рабочем стенде.

Если сертификат не выпускается, смотрите `docker compose logs caddy`: чаще всего
это DNS, закрытый 80/443, CGNAT или включённый прокси Cloudflare.

## 7. Бэкапы

Скрипт `scripts/backup.sh` снимает дамп PostgreSQL и архив загруженных файлов:

```powershell
wsl -e sh -c "cd /mnt/d/<путь-к-проекту> && BACKUP_DIR=/mnt/d/vkr-backups sh scripts/backup.sh"
```

Настройте запуск раз в сутки через Планировщик заданий Windows (программа `wsl.exe`,
те же аргументы). Дополнительно сохраните `.env` в защищённое место: без `APP_KEY`
не расшифруются старые сессии, а без пароля БД не восстановится дамп.

Требования:

- бэкапы хранить только в РФ (отдельный диск, российское объектное хранилище);
- копия — вне системного диска ПК;
- периодически проверять восстановление на тестовом стенде;
- `RETENTION_DAYS` не больше срока, обещанного в политике (сейчас 30 дней).

Подробности — [backup.md](backup.md).

## 8. Обновления

Всё делает `scripts\deploy.cmd` — двойным кликом из папки проекта или из PowerShell:

```powershell
.\scripts\deploy.cmd

# то же, но без свежего дампа и без обновления кода
.\scripts\deploy.cmd -SkipBackup -SkipPull
```

Скрипт проверяет, что Docker запущен, открыта прод-ветка `redesign/underground` и в рабочей копии
нет локальных правок, затем снимает бэкап, делает `git pull --ff-only`, `docker compose build app`,
`docker compose up -d` и до четырёх минут ждёт ответа `http://127.0.0.1:8080/up`.
На первой ошибке останавливается: контейнер до перезапуска не трогается, сайт остаётся на прежней
версии. Бэкап идёт через WSL (`scripts/backup.sh`), поэтому без WSL запускайте с `-SkipBackup`.

Без параметров скрипт показывает меню:

1. **Полный релиз** — бэкап, `git pull --ff-only`, сборка, перезапуск, ожидание `/up`.
2. **Статус и логи** — контейнеры, что выкачено (коммит и дата образа), свободное место,
   последние 50 строк логов `app`.
3. **Откат на предыдущий образ** — перед каждой сборкой текущий образ помечается
   `vkr-blog/app:previous`; откат возвращает тег и перезапускает контейнер без пересборки.
   Миграции БД назад не откатываются — если в релизе была миграция, база останется новой.
4. **Очистка** — висячие образы и кеш сборки старше недели; после успешного релиза выполняется сама.

Релиз, откат и очистка дописывают лог в `backups\deploy-YYYYMMDD-HHMMSS.log` (время, коммит, шаги,
результат). Логи лежат рядом с бэкапами, поэтому удаляются тем же правилом `RETENTION_DAYS`.

Ручной порядок — если скрипт недоступен:

```powershell
wsl -e sh -c "cd /mnt/d/<путь-к-проекту> && sh scripts/backup.sh"
git pull --ff-only
docker compose build app
docker compose up -d
```

Миграции применяются автоматически в entrypoint. Обновляйте и внешние образы:
`docker compose pull db caddy`, затем `docker compose up -d`.

## 9. Безопасность

- Наружу открыты только 80/443; `8080` слушает `127.0.0.1`; у `db` нет проброса портов.
- `APP_DEBUG=false`, сильные пароли, `.env` не в git и с ограниченным доступом.
- Не открывайте наружу RDP/SSH; обновляйте Windows и Docker.
- Следите за диском и логами: `docker compose logs --tail=100 app`.
- Домашний IP виден всем. При атаке поможет защита провайдера или российский
  reverse-proxy/CDN; это должно быть отражено в политике как обработчик ПД.
- Cloudflare Proxied/Tunnel не используйте.

## 10. Юридические требования

- 152-ФЗ: базы с персональными данными граждан РФ — в России. Домашний ПК в РФ
  подходит; бэкапы и почта тоже должны быть в РФ.
- До первых реальных пользователей подайте уведомление в Роскомнадзор через
  `pd.rkn.gov.ru`. Об изменениях сведений — в течение 15 дней.
- В политике должно быть верно: хранение в РФ, трансграничной передачи нет. Это
  ломают Cloudflare Proxied/Tunnel, зарубежная почта, аналитика, CDN и облачные
  бэкапы.
- IP-адрес, User-Agent и логи РКН относит к персональным данным — они уже хранятся
  локально, это нормально.
- Проверьте `config/legal.php` и тексты `/privacy`, `/terms`, `/consent`.
- Возрастная маркировка — если решите её ставить; cookie-баннер нужен только при
  появлении аналитики.

Это не юридическое заключение: перед публичным запуском тексты стоит показать юристу.
Подробнее — [legal.md](legal.md).

## 11. Если что-то не работает

| Симптом | Что проверить |
|---|---|
| Сертификат не выпускается | DNS, 80/443 снаружи, CGNAT, логи Caddy, Cloudflare не в режиме Proxied |
| Порт 80 занят | IIS (`W3SVC`), другой nginx, `Get-NetTCPConnection` |
| Сайт недоступен после перезагрузки | Docker Desktop не стартовал, питание/сон, `docker compose ps` |
| Логин не держится | `SESSION_SECURE_COOKIE=true` только при HTTPS, `APP_URL` совпадает с доменом |
| Картинки 404 | `APP_URL`, символическая ссылка `public/storage`, том `storage` |
| Mixed content | `APP_URL=https://…`, `trustProxies`, пересоздать `app` через `up -d` |
| Медленно | скорость отдачи домашнего интернета; картинки уже сжимаются в WebP |
| Провайдер режет порты | белый IP/тариф с сервером либо российский VPS |

## 12. Ограничения домашнего хостинга

Нет SLA: свет, интернет, перезагрузки Windows и износ диска — реальные риски.
Резервная копия на отдельном диске обязательна. Если проект вырастет или появятся
реальные пользователи, переезд на российский VPS занимает те же команды: скопировать
проект и тома, поправить `.env`, поднять профиль `https`. Для ВКР домашний стенд с
белым IP — рабочий и легальный вариант, если в разделе правового обеспечения
описаны локализация, уведомление РКН и отсутствие трансграничной передачи.
